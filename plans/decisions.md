**N9. The provenance mode: per call, or fixed for a run** (jhuggins on #587, 2026-10-18; PR #597, question 3).
*Background.* Decision OD2 (2026-10-18) makes the provenance mode a setting resolved when each call opens (step PV), because inside an open `workflow_run` a `config.provenance.using(mode=OFF)` block today reads OFF while provenance is still recorded, a silent conflict. jhuggins agrees replay does not depend on the rule (the mode only decides whether a call captures its callable anchor and randomness recipe, and keys do not depend on it), but prefers keeping the mode fixed for a run and having a block that changes it inside an open run raise: with a per-call mode, a block can switch provenance off for some calls, and a later result's ancestry then stops at those calls with no sign of the gap. For skipping the bookkeeping of a heavy intermediate computation, LIGHTWEIGHT already lets intermediates be garbage-collected, and wrapping the computation in one `@function` records it as a single step.
*Options.* (1) Keep the per-call mode (OD2). (2) jhuggins's rule: the mode is fixed when the outermost `workflow_run` opens, and a `config.provenance.using` block that changes it inside an open run raises, naming the run's mode; PV becomes that raise, plus the removal of the Prefect payload's copy. (3) Middle: the mode is per call, but a block may only raise the level inside an open run (OFF → LIGHTWEIGHT → FULL), and a block that lowers it, OFF above all, raises; so no gap appears silently, and a user can still record more detail for one call.
*Recommendation.* (2), with (3) as the alternative if recording more detail for one call matters. A gap in ancestry that nothing reports is the larger harm, and the conflict OD2 removed is removed by the raise as well. PV's session snapshot (`session_config_values` for every section, read inside evaluation points) does not depend on this choice and stays in PV.

**N19. A permanent refusal for `*` between laws** (p4 M3) [A.1, C.1, B.6].

### The execution design

**N22. The name of the property that makes an opaque `Function` embeddable** (p3 B1).
*Background.* `execution-layer.md` calls an output declaration **complete** when a host callback can return its value (a numeric array or a record of them, with dtypes, and shapes bound by the declared inputs; § 6.2 now defines it precisely). `declarations-and-addressing-io.md` uses "complete" for "has no type hole" (§ 3.3, § 5.3), and "completes" for a third relation (§ 2.1, B.3). An implementer who reads the `-io` sense builds the wrong check.
*Options.* (1) "Stageable output declaration" for the execution property, defined over the `-io` kinds, with `-io` F.1 saying "an embeddable `Function` needs a stageable output declaration". (2) "Shape-determined". (3) Keep "complete" and rename the `-io` sense to "hole-free", which reopens the accepted plan.
*Recommendation.* (1), since the name says what the property allows; E1 then puts "stageable output declaration" in the glossary.

**N23. The public target interface of E6** (p3 B4).
*Background.* `make_posterior` already exists with another signature (`make_posterior(chains, parents, method, *, annotations, event_spec, field_order, weights, label, **meta)`, 28 uses); `docs/api/extending.md` documents `InferenceMethod.execute(self, target, /, **options)` on the private `_UnnormalizedConditional`; the layout of `log_density`'s argument (flat or record), the initial positions, and the unconstraining bijectors are unstated; `ModelFactors` is private; and the plan does not say where `key` appears or what `run_seed`'s 30 uses become.
*Options.* (a) `InferenceMethod.execute(target: InferenceTarget, /, *, key: Array, **options)`, with `_UnnormalizedConditional` implementing `InferenceTarget`; the existing `make_posterior` renamed to the public builder, its signature written field by field with a Today → Proposed block; `ModelFactors` public; `log_density(position: Array) -> Array` in the flat layout with `unflatten(position) -> Record`. (b) Keep `execute(target, **options)` and add `target.inference_view() -> InferenceTarget`.
*Recommendation.* (a), with E6's done-condition made concrete: "the `ImportanceSampling` example of `docs/api/extending.md`, rewritten against `InferenceTarget`, runs through `condition_on.using(method=...)` and gives the same draws at one seed under `workflow_run`; `run_seed` and the private import of `ModelFactors` no longer appear in `inference/`".

**N24. What `vectorized=True` receives for shared and record arguments** (p3 M8).
*Background.* A vectorized callable "accepts every array argument with an extra leading axis". Whether an argument every evaluation point shares is stacked or passed once depends on the call (in `forward(theta=prior, data=y)` only `theta` varies), which the callable cannot know; and an input whose spec is a `RecordSpec` is one input.
*Options.* (a) Every array leaf of every argument is stacked to the chunk's length, shared ones as read-only `np.broadcast_to` views, so nothing is copied; a record argument is stacked leaf by leaf, and a derivative receives the same stacking. (b) Shared arguments are passed unstacked, which needs a per-call declaration the callable cannot make.
*Recommendation.* (a).

**N25. A record-valued output from opaque code, and the check relation** (p3 M9).
*Background.* `pure_callback` requires the host to return exactly the pytree of its `ShapeDtypeStruct`s. The plans do not say whether an opaque body returns a `Record` or may return a mapping, whether the per-point check is its own notion or `-io`'s **conforms** (§ 2.1, which admits a same-kind cast and any dtype when none is declared), or whether the keyword form `OutputSpec(forward=T)` checks the bare array or `{forward: …}`.
*Options.* (1) "Each output must conform (`-io` § 2.1) to `output_spec.term_spec`; a base output is the bare array, never `{name: array}`. A record output may be a `Record` or a mapping with exactly the spec's fields, converted to a `Record` in canonical order. A conforming output is cast to the declared dtype, warning once per call when the cast loses precision; one that does not conform is an `invalid` failure." (2) A separate check of tree structure, shape, and dtype.
*Recommendation.* (1), so the two plans share one relation (directive 11).

**N26. How claims combine, for targets that are not `Function`s** (p3 M11).
*Background.* E2 removes `is_jax_traceable`, but the densities inference probes today are plain closures (`likelihood_flat(factors)` and the densities of `_blackjax_mcmc.py`, `_blackjax_rwmh.py`, `_tfp_mcmc.py`, `_empirical_reweighting.py`), with no probe result and no claim; § 6.2's three bullet rules are not an algorithm, and a law has no claims today.
*Options.* (a) Every `Distribution` and `ConditionalDistribution` gets a derived, cached `traceability` (traceable, embeddable, or host-only) from its parts: families are traceable; a kernel's is fixed by its construction-time abstract evaluation (kept, not merged into the probe); a law built from functions has a probe result keyed as probe rule 3 says; a joint's is the meet of its factors', written as a table. (b) The inference target's flat density is probed once per input structure, and the result is stored on the target.
*Recommendation.* (a), with the meet as a table and "the five probes" listed precisely.

**N27. The `jax` executor before compiled lifting, and `batch_size`** (p3 M17).
*Background.* Before compiled lifting (which joins the core only if time allows), the plan does not say whether `jax` runs an eager `jax.vmap`, which registers tokens at once under registration rule 5, or a stored JAX program. `batch_size` maps with `lax.map`, a staging trace, so an opaque call inside a traceable lifted body would stage token 0 and warn wrongly.
