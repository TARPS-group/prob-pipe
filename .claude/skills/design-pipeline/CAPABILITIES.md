# ProbPipe capabilities

This file names the ProbPipe API that a pipeline uses.
Its first table lists the routes by which a user's model enters ProbPipe, and the tables after it list the needs of a pipeline by workflow stage.
Each row names the ProbPipe entry points, the page that shows them in use, and the stage of the workflow checklist in [RESOURCES.md](./RESOURCES.md) Part 1 that it serves.
The phase files name the needs, and this file names the API.
`<corpus>/INDEX.md` lists every export with its signature, so it answers what this file leaves out.
Confirm each entry point by the ground rule "Confirm every API name" of [INSTRUCTIONS.md](INSTRUCTIONS.md#ground-rules) before you use it.

The entry-point column holds only names that import, in one of three forms:

1. a top-level export, such as `Normal`;
2. an attribute of a top-level export, such as `condition_on.using`;
3. a full path, such as `probpipe.validation.interval_coverage`.

A test imports each of them.
The last column holds the expressions and the conventions that are not names, such as the merge `likelihood & prior`.

## Bring any model

A model enters ProbPipe in the form in which the user already has it, so start from the user's code or mathematics.
Any model that the user can write as a log density, a sampler, or both enters by one of the routes of this table.
PyMC and Stan write standard statistical structure, such as random effects and CAR priors, with their own distributions or a few lines of code, and the route in JAX writes any density or sampler, such as a mechanistic model or a simulator.
On that last route, `glm_likelihood` writes a generalized linear model in one call.
Step 3 of [phases/4-proposal.md](phases/4-proposal.md) chooses the route of a model written for the project.
The route decides which inference methods and checks apply, and the last column states them.
One model can combine routes, such as a likelihood written in JAX that calls a solver wrapped as a `function`.
The built-in families and the hierarchical example of the user guide are conveniences for common cases.

The batched recipe of the validation, for a joint model `model = likelihood & prior` whose parameters are the fields `parameters` and whose data is the field `"y"`, with `n` datasets simulated from prior draws and `m` at a chosen value, is below.
In a pipeline it is the body of a step function, such as `validate(model, likelihood, settings)`, whose settings object holds `n`, `m`, `method`, and `options`, and which returns the grade and the table of the validation that `record_validation()` records.
`validate()` of `templates/pipeline_skeleton.py` runs its first part, over the prior draws, as such a function.

```python
# All the simulated datasets in one draw. The level is renamed so that a later
# sample of the posteriors, which adds a level "sample", keeps distinct levels.
with workflow_run(seed=1):
    sims = sample(model, sample_shape=(n,)).with_level_names(sample="sim")
datasets = sims.without(*parameters)  # a RecordBatch of the data alone
truth = sims.without("y").to_vector()  # (sim, coordinate)

# One sweep: a DistributionBatch with one posterior per dataset.
with workflow_run(seed=2):
    posteriors = condition_on.using(method=method, method_options=options)(model, datasets)

# The diagnostics of each fit.
summary = summarize(posteriors)
rhat = summary["r_hat"].to_vector()  # (sim, coordinate)
ess_bulk = summary["ess_bulk"].to_vector()
divergences = np.array(
    [int(p.annotations["arviz"]["sample_stats"]["diverging"].sum()) for p in posteriors]
)

# Coverage, z-scores, and contraction as array operations over the fits.
bounds = quantile(posteriors, jnp.array([0.05, 0.95])).to_vector()  # (sim, 2, coordinate)
coverage = ((bounds[:, 0] <= truth) & (truth <= bounds[:, 1])).mean(axis=0)
z_score = (summary["mean"].to_vector() - truth) / summary["sd"].to_vector()
with workflow_run(seed=3):
    prior_draws = sample(model, sample_shape=(4000,)).without("y").to_vector()
contraction = 1 - summary["sd"].to_vector() ** 2 / prior_draws.var(axis=0)

# Recovery at one chosen value `theta`, a mapping from each parameter to its value,
# with m datasets drawn from the likelihood at that value.
with workflow_run(seed=4):
    at_theta = sample(condition_on(likelihood, theta), sample_shape=(m,)).raw
    chosen = condition_on.using(method=method, method_options=options)(
        model, RecordBatch({"y": at_theta}, "sim")
    )
    draws = sample(chosen, sample_shape=(1000,)).to_vector()  # (sim, draw, coordinate)
theta_vector = np.concatenate([np.ravel(theta[name]) for name in parameters])
chosen_summary = summarize(chosen)
sd = chosen_summary["sd"].to_vector()
deviation = draws - draws.mean(axis=1, keepdims=True)
posterior_cov = np.einsum("sdi,sdj->sij", deviation, deviation) / (draws.shape[1] - 1)
prior_precision = np.linalg.inv(np.cov(prior_draws, rowvar=False))
pull = posterior_cov @ prior_precision @ (prior_draws.mean(axis=0) - theta_vector) / sd
centered = (chosen_summary["mean"].to_vector() - theta_vector) / sd - pull  # (sim, coordinate)
bias = np.abs(centered.mean(axis=0)) * np.sqrt(m)  # in standard errors


def bound(tail: float, results: int) -> float:
    """The bound whose two-sided tail over `results` results totals `tail`."""
    return float(scipy.stats.norm.isf(tail / (2 * results)))


largest = np.abs(centered).max()  # the largest single miss
passed = bias.max() <= bound(0.0455, bias.size) and largest <= bound(0.0455, centered.size)
```

The recipe orders the coordinates of each array, such as `truth`, `theta_vector`, and the draws, by the fields of the parameters, so the arrays align.
RESOURCES.md stage D step 6 defines the bias, the single misses, and their bounds, and with several chosen values, `bias` and `centered` stack over them before `bound` counts the results.
The fits that a remedy of RESOURCES.md stage E reruns are one sweep over their datasets, `RecordBatch({"y": datasets["y"].raw[divergences > 0]}, "sim")`.
A `PyMCModel` separates no likelihood, so draw its datasets at θ with PyMC: `pm.draw(pm.do(build(), theta)["y"], draws=m, random_seed=seed)` fixes the parameters of `theta`, given as arrays, and draws the other random variables, such as group effects, afresh for each dataset.

| Condition on the data | `condition_on`, `condition_on.using`, `condition_on.check`, `inference_method_registry`, `inference_method_registry.check`, `condition_on_nutpie` | `docs/user_guide/06_conditioning_and_inference.ipynb`, section "Choosing an inference method" | E. Fit and diagnose the computation | `condition_on(model, observed)` selects a method by the capabilities of the model, as the routes of "Bring any model" state, and its selection is a reasonable default. `condition_on.check(model, observed)` reports the method that a call would select, and `inference_method_registry.check(model, observed, method=name)` reports why a method declines. `condition_on.using(method=name)` runs another method that applies. After a run, `posterior.provenance.metadata["method"]` names the method that ran. `<corpus>/INDEX.md` lists the methods with their priorities. The NUTS methods take different settings in `method_options=`. `blackjax_nuts` takes `num_warmup`, `num_results`, `num_chains`, `step_size`, `init`, `target_accept_prob`, which is 0.8 unless set, and `max_tree_depth`, which is 10 unless set, so it serves step 2 of the bullet "Remedy divergences in this order" of RESOURCES.md stage E. `tfp_nuts` runs when named and takes `target_accept_prob`, which is 0.75 unless set. Its warmup adapts the step size and no mass matrix, so on a badly scaled posterior it can need a longer warmup than `blackjax_nuts` and give a lower ESS, and the ESS of the two runs decides between them. Its sample statistics hold neither `energy` nor `num_integration_steps`, so its runs check neither the E-BFMI nor the tree depth. `nutpie_nuts`, `pymc_nuts`, and `cmdstan_nuts` take no target acceptance rate and no maximum tree depth, which are ProbPipe gaps, so for a PyMC or Stan model call `condition_on_nutpie(model, data, target_accept=0.95, maxdepth=12)`, which passes each keyword to nutpie's sampler. `nutpie_nuts` and `condition_on_nutpie` compile the model on every call, and a posterior's provenance records neither the run time nor the backend's seed, which are ProbPipe gaps. `blackjax_nuts` and `tfp_nuts` start each chain from its own draw unless `init` sets the starting point, as RESOURCES.md stage E asks, whereas `blackjax_rwmh` starts every chain from one state, which weakens R-hat as a check for separate modes and is a ProbPipe gap. ProbPipe computes in float32 unless the program runs `jax.config.update("jax_enable_x64", True)` before it creates any array, and RESOURCES.md stage E says when MCMC needs double precision. |

One remedy writes θ = max(y) + exp(u), gives `u` the prior density of θ there times exp(u), and fits with `blackjax_nuts`. The validation then fits each simulated dataset with the model built from its own maximum. The other remedy is `blackjax_rwmh` from an `init` inside the support. In quick start, the baseline is a law with a fixed support, such as `LogNormal` or a Gumbel law. ProbPipe has no extreme-value family, which is a ProbPipe gap, and `distribution(log_prob=..., sample=...)` writes one. |
| Use draws from another program | `EmpiricalDistribution`, `NumericRecordBatch` | `docs/user_guide/08_conversion_and_updating.ipynb`, section "Empirical distributions" | E. A component written with ProbPipe's existing laws and a fixed transform is often the simplest interface. An intrinsic CAR prior with its sum-to-zero constraint, for example, is a fixed matrix times independent standard `Normal` variables, and the matrix comes once from the eigendecomposition of the precision matrix of the adjacency graph.
