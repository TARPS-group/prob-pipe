# ProbPipe capabilities

This table maps each need of a pipeline to the ProbPipe entry points that meet it, the page that shows them in use, and the stage of the workflow checklist in [RESOURCES.md](./RESOURCES.md) Part 1 that it serves.
The phase files name the needs, and this file names the API.
`<corpus>/INDEX.md` lists every export with its signature, so it answers what this table leaves out.
Before you use an entry point, search the corpus for its docstring.
Then run `check_symbols.py` on the code that uses it.

The entry-point column holds only names that import, in one of three forms:

1. a top-level export, such as `Normal`;
2. an attribute of a top-level export, such as `condition_on.using`;
3. a full path, such as `probpipe.validation.interval_coverage`.

A test imports each of them.
The last column holds the expressions and the conventions that are not names, such as the merge `likelihood & prior`.

| Need | Entry points | Example | Stage | How it is used |
|---|---|---|---|---|
| Hold the observed data and the covariates | `Record`, `NumericRecord`, `RecordBatch`, `condition_on`, `probpipe.families.glm_likelihood` | `docs/user_guide/02_values_and_records.ipynb`, section "Records" | A. Before writing a model | The observed values are a mapping from the model's output names to arrays, which is the form that `condition_on` takes. The covariates are arrays that the likelihood holds, as `glm_likelihood` takes them through `X=`. A structured value is a `Record` or a `NumericRecord`, and several datasets are a `RecordBatch`. |
| Write independent priors | `Normal`, `HalfNormal`, `Gamma`, `Beta` | `docs/user_guide/03_distributions.ipynb`, section "Parametric families" | B. Priors | Each parameter's prior is a distribution family, and the families merge into one joint law with `&`. `<corpus>/INDEX.md` lists every family. |
| Write a prior that depends on other parameters | `conditional_distribution` | `docs/user_guide/04_joint_models.ipynb`, section "Chaining factors: a hierarchical model" | B. Priors | A function of the parent parameters returns the law of the child parameter. |
| Constrain a parameter or transform it | `positive`, `bijector_for` | `docs/user_guide/03_distributions.ipynb`, section "Supports" | B. Priors | A constraint such as `positive` names a support, and `bijector_for` gives the canonical bijector from the real numbers onto it. |
| Write a regression likelihood | `probpipe.families.glm_likelihood`, `probpipe.families.PoissonFamily`, `probpipe.families.BernoulliFamily` | `docs/user_guide/04_joint_models.ipynb`, section "Generalized linear models" | A. Before writing a model | `glm_likelihood` builds the likelihood of a generalized linear model from a response family and the covariates `X=`. |
| Write any other likelihood | `conditional_distribution` | `docs/user_guide/04_joint_models.ipynb`, section "A conditional distribution from a function" | A. Before writing a model | A function of the parameters returns the law of the data. |
| Form the joint model | `conditional_distribution`, `probpipe.families.glm_likelihood` | `docs/user_guide/04_joint_models.ipynb`, section "Merging a joint model with `&`" | A. Before writing a model | The model is the merge `likelihood & prior`. |
| Use an existing Stan or PyMC model | `StanModel`, `PyMCModel` | `docs/user_guide/06_conditioning_and_inference.ipynb`, section "Models written in PyMC or Stan" | A. Before writing a model | The extras `stan` and `pymc` install the backends, as `docs/get_started/installation.md` describes. |
| Wrap a simulator | `conditional_distribution`, `distribution` | `docs/tutorials/06_simulating.ipynb`, section "2. A distribution that can only draw" | I. Simulators and expensive models | The function of a `conditional_distribution` returns a law that samples, such as one built with `distribution(sample=...)`. |
| Draw from a law reproducibly | `sample`, `workflow_run` | `docs/user_guide/09_how_results_are_computed.ipynb`, section "Reproducible draws" | C. Prior predictive checks, J. Reproducibility and communication | `workflow_run(seed=...)` opens a random execution scope that the workflow owns, so a seed fixes the draws inside it. |
| Run a prior predictive check | `predictive_check`, `sample` | `docs/tutorials/02_fitting.ipynb`, section "8. A predictive check" | C. Prior predictive checks | `predictive_check(likelihood, prior, statistics)` takes the prior as its law, and `sample` of the joint model draws simulated data. |
| Validate the computation on realistic simulated data | `sample`, `condition_on`, `condition_on.using`, `probpipe.validation.simulation_based_calibration`, `probpipe.validation.interval_coverage` | `docs/user_guide/07_checking_results.ipynb`, section "Simulation-based calibration" | D. Validate the computation on simulated data | `sample` of the joint model simulates parameters and data together, at the real covariates that the likelihood holds, and the code masks each simulated dataset to the missingness pattern of the real data. `condition_on.using(method=name)` fits each simulated dataset with the planned method. `interval_coverage(draws, truth)` reports whether each central interval of one posterior covers the true value, so its average over the simulated datasets estimates the coverage. It takes an array of draws, so it also scores the draws of an estimand against the estimand's true value. `simulation_based_calibration(model, observed=..., num_simulations=..., num_posterior_draws=..., method=...)` ranks each parameter among its posterior draws, and its `posterior=` argument takes an amortized posterior, which it evaluates without a fit. It ranks parameters only, so a data-dependent test quantity, the posterior z-score, and the posterior contraction are computed in the pipeline's own code and recorded as a ProbPipe gap. |
| Condition on the data | `condition_on`, `condition_on.using`, `condition_on.check`, `inference_method_registry`, `inference_method_registry.check` | `docs/user_guide/06_conditioning_and_inference.ipynb`, section "Choosing an inference method" | E. Fit and diagnose the computation | `condition_on.check(model, observed)` reports the method that a call would select, and `inference_method_registry.check(model, observed, method=name)` reports why a method declines. `condition_on.using(method=name)` runs a named method. After a run, `posterior.provenance.metadata["method"]` names the method that ran. `<corpus>/INDEX.md` lists the methods with their priorities. |
| Diagnose MCMC | `probpipe.diagnostics.add_mcmc_diagnostics`, `probpipe.diagnostics.add_rhat`, `probpipe.diagnostics.add_ess`, `probpipe.diagnostics.add_mcse` | `docs/user_guide/07_checking_results.ipynb`, section "MCMC diagnostics" | E. Fit and diagnose the computation | `add_mcmc_diagnostics` computes the rank-normalized R-hat, the bulk and tail ESS, the MCSE of each parameter's mean and standard deviation, and the number of divergences. It warns when an R-hat exceeds 1.01 or an ESS falls below 400 in total, which is 100 per chain for four chains. The results are in `posterior.diagnostics`, and the ArviZ data is `posterior.annotations["arviz"]`. ProbPipe computes neither the E-BFMI, the tree depth, the nested R-hat, nor the MCSE of a derived estimand. ArviZ computes the E-BFMI with `bfmi` and the nested R-hat with `rhat_nested` from the ArviZ data, and the tree depth follows from the sample statistic `num_integration_steps`. The sample statistics hold `energy` and `num_integration_steps` only for samplers that record them, such as `blackjax_nuts`. ArviZ's `mcse` gives the MCSE of an estimand from its draws per chain. Record each criterion of RESOURCES.md stage E that the run cannot check as a ProbPipe gap. |
| Check the model against the data | `predictive_check`, `probpipe.diagnostics.add_ppc`, `probpipe.diagnostics.add_loo` | `docs/user_guide/07_checking_results.ipynb`, section "Posterior predictive checks" | F. Check the model against the data | `predictive_check(likelihood, posterior, statistics, observed)` replicates the data from the posterior. `add_loo(posterior, model=..., data=...)` computes PSIS-LOO over the observations, and `posterior.diagnostics.loo` reads the elpd and the summary of the Pareto k̂, such as `pareto_k_max` and `pareto_k_bad_count`. For leave-one-group-out, pass a pointwise log likelihood summed within each group as `log_likelihood=`. ProbPipe has no leave-future-out or blocked cross-validation, no k-fold cross-validation, no LOO-PIT, and no stacking. ArviZ computes k-fold cross-validation with `loo_kfold`, LOO-PIT with `loo_pit`, and stacking weights with `compare(..., method="stacking")`, from `posterior.annotations["arviz"]`. Record each scheme that the pipeline needs and ProbPipe lacks as a ProbPipe gap. |
| Compare models and datasets in one sweep | `condition_on`, `DistributionBatch`, `RecordBatch` | `docs/user_guide/07_checking_results.ipynb`, section "Comparing models with leave-one-out cross-validation" | G. Compare, expand, and combine models; H. Understand the fitted model | `condition_on` over a `DistributionBatch` of models, or a `RecordBatch` of datasets, returns a `DistributionBatch` of posteriors. A batch of models under alternative priors is a sensitivity analysis. |
| Draw bootstrap replicates of the data | `BootstrapReplicateDistribution` | `docs/user_guide/08_conversion_and_updating.ipynb`, section "Bootstrap distributions" | G. Compare, expand, and combine models | The posteriors conditioned on the replicates together form a bagged posterior. |
| Compute downstream quantities | `function`, `mean`, `quantile`, `expectation` | `docs/user_guide/05_functions_and_lifting.ipynb`, section "Calling a function on a distribution" | H. Understand the fitted model | A function decorated with `@function` and called on coupled marginals of the posterior, such as `f(posterior["a"], posterior["b"])`, draws them jointly. |
| Update as observations arrive | `iterate`, `with_conversion`, `with_resampling` | `docs/user_guide/08_conversion_and_updating.ipynb`, section "Updating as observations arrive" | Phase 4 step 8 | Tutorial 5 updates a forecast year by year with them. |
| Fit a model that can only be simulated | `learn_amortized_posterior`, `learn_amortized_likelihood`, `learn_amortized_ratio`, `condition_on` | `docs/tutorials/06_simulating.ipynb`, section "4. An amortized posterior" | I. Simulators and expensive models | `condition_on` runs approximate Bayesian computation through the method `pyabc_smcabc`, and the `learn_amortized_*` functions train BayesFlow networks. A ratio from `learn_amortized_ratio` is a log likelihood up to a constant that does not depend on the parameters, which is valid for `condition_on` and invalid for LOO, WAIC, and model comparison, as its docstring states and RESOURCES.md stage F explains. |
| Emulate an expensive model | `GaussianRandomFunction`, `RandomFunction` | `docs/api/random_functions.md` | I. Simulators and expensive models | A Gaussian process emulator is a random function, which is a law over functions. |
| Score an approximate posterior | `probpipe.validation.score_posterior`, `probpipe.validation.Reference.from_draws`, `probpipe.validation.std_ratios` | `docs/user_guide/07_checking_results.ipynb`, section "Interval coverage of one posterior" | E. Fit and diagnose the computation | `score_posterior(approx, Reference.from_draws(mcmc_draws))` compares an approximate posterior with a reference built from an MCMC fit to the same data, as RESOURCES.md stage E requires. `std_ratios` gives each coordinate's ratio of standard deviations, and a ratio below one shows a variance that the approximation underestimates. `docs/api/validation.md` lists the metrics of `probpipe.validation`. |
| Run a pipeline at scale | `executor_registry` | `docs/user_guide/ray.md` | Phase 4 step 8 | The extra `prefect` runs functions as Prefect tasks, and Prefect runs them on Ray. |
| Record how each result was computed | `workflow_run`, `replay_run`, `provenance_ancestors` | `docs/user_guide/09_how_results_are_computed.ipynb`, section "Provenance" | J. Reproducibility and communication | Each result's `provenance` describes how the result was produced, and `provenance_ancestors` returns the results it was computed from. |
| Meet a need ProbPipe does not cover | `function`, `conditional_distribution`, `StanModel`, `PyMCModel` | `docs/api/extending.md` | Every stage | Most gaps have one of three workarounds: a custom `@function`, a likelihood built with `conditional_distribution`, or a wrapped Stan or PyMC model. `docs/api/extending.md` describes how to register a new inference method. |
